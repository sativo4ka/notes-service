# Архитектура Notes Service

## 1. Основной пользовательский сценарий

Пользователь запрашивает список заметок. Запрос проходит через API Gateway в Notes API. В целевой архитектуре Notes Service проверяет Redis Cache: если нужные данные есть в кэше, они возвращаются пользователю; если данных нет, Notes API получает их из PostgreSQL, сохраняет результат в Redis и возвращает ответ. При изменении или удалении заметки кэш соответствующей записи должен быть обновлён или очищен.

## 2. C4 Level 1 — System Context

На контекстной диаграмме показаны пользователь и Notes Service как программная система. Пользователь взаимодействует с системой по HTTPS/REST. На этом уровне внутренние контейнеры и хранилища не раскрываются.

## 3. C4 Level 2 — Container

- **Пользователь / HTTP-клиент** — отправляет запросы к API.
- **API Gateway (Nginx)** — единая точка входа; принимает HTTP-запросы и направляет их в Notes API.
- **Notes API (Node.js + Express)** — обрабатывает REST-запросы и выполняет операции с заметками.
- **PostgreSQL** — основное постоянное хранилище; содержит таблицу `notes`.
- **Redis Cache** — дополнительное временное хранилище для часто запрашиваемых данных.

## 4. C4 Level 3 — Component

Внутри Notes API предлагается следующее логическое разделение:

- **Notes Controller** — принимает HTTP-запросы, извлекает параметры и формирует HTTP-ответы. В текущей реализации эту роль выполняют Express-обработчики в `server.js`.
- **Notes Service** — содержит бизнес-логику операций с заметками и координирует доступ к хранилищам. Это предлагаемое выделение слоя.
- **Notes Repository** — отвечает за SQL-запросы к PostgreSQL. В текущей реализации SQL-запросы находятся непосредственно в обработчиках `server.js`; отдельный модуль Repository пока не выделен.
- **Cache Repository** — изолирует операции чтения, записи и инвалидации Redis. Это предлагаемый компонент целевой архитектуры.

## 5. Почему выбран Redis Cache

Для сервиса заметок типичны повторные запросы списка заметок и отдельных записей. Redis хранит часто используемые результаты в памяти и может уменьшить количество повторных чтений из PostgreSQL. PostgreSQL остаётся источником постоянных данных: потеря или очистка кэша не должна приводить к потере заметок.

## 6. Текущее состояние и целевая архитектура

В опубликованном репозитории уже присутствуют Node.js, Express, PostgreSQL и Docker Compose. CRUD-маршруты и SQL-запросы находятся в `server.js`.

**API Gateway (Nginx), Redis Cache и отдельные модули Controller/Service/Repository показаны как предлагаемое архитектурное развитие.** Диаграммы описывают целевую архитектуру для задания и не утверждают, что эти расширения уже запущены или реализованы в коде.
